## Original finding

The current `FOMOptionOnly.java` results should be treated as preliminary and should not be used as final Q1 ablation evidence without additional validation.

After comparing `FOMOptionHashOnly`, `FOMOptionSparseOnly`, and `FOMOptionWSBOnly` against Full FOM, all three option-only variants have identical deterministic counters for all 84 configurations:

- `Candidates`: 84/84 match
- `Fusions`: 84/84 match
- `SupportOps`: 84/84 match
- `FreqPatterns`: 84/84 match

This means the option-only plots mostly compare Java implementation overhead rather than demonstrating different algorithmic work reductions.

## Why Full FOM can appear slower than one option

1. The previous Full FOM benchmark in `benchmark/fom/FOM_summary_avg.csv` was generated by `run_fom_benchmark_canonical.ps1`, which enables `-Dcanonical=...`. Option-only runs do not write canonical pattern-support files.

2. `FOM.java` includes the full bitmap/proactive-consumption implementation, including `consumedMaskP` handling. Some option-only paths use simpler scalar arrays or simpler bitmap flow, so wall-clock time can be lower even when the algorithmic counters are identical.

3. The current option-only modes are not yet a clean "OPF baseline + exactly one optimization" decomposition. They are implementation variants sharing much of the same candidate/support behavior.

## Consequence

Do not claim from the current option-only figure that one individual option outperforms the full three-option FastOPF design.

The current option-only results can only be described as an implementation diagnostic unless the ablation is redesigned.

## Recommended fix

For a defensible ablation study, implement a single configurable engine with explicit feature flags:

- Hash join: on/off
- Sparse bitmap/vectorized support: on/off
- WSB pruning: on/off
- Canonical output: always off during timing

Then run the same benchmark protocol for:

- OPF baseline
- Hash only
- Sparse only
- WSB only
- Hash + Sparse
- Hash + WSB
- Sparse + WSB
- Full FastOPF

Each variant should also write canonical output once, outside the timed benchmark, to verify exact/tolerant equivalence.
